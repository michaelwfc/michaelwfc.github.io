# 高频题的回答思路

1. 你怎么理解 Agent 系统？拆解核心模块。

这题是开场题，答得好坏直接决定面试官后面往多深挖。我的答法：

先把定义给准：Agent 是以 LLM 为核心、能自主规划任务、调用工具、并根据环境反馈动态调整行动的系统。关键词是"自主"和"反馈闭环"，这两个词是后面所有展开的锚点。

然后拆四个模块：规划（Planning，含任务分解和反思）、记忆（Memory，短期 context + 长期存储）、工具（Tool Use，function calling / MCP）、执行控制（循环驱动、终止条件、异常兜底）。

最后主动补一刀：Agent 和 workflow 的本质区别是路径决策权在谁手里。这句话我每场都说，每场都能把面试官的兴趣勾起来，主动权就到了我手里：后面他大概率顺着这个问，而那部分我准备得最熟。

2. ReAct 和 Plan-and-Execute 分别适合什么场景？怎么避免死循环？

前半段：ReAct 是边想边做，Thought → Action → Observation 循环，每步看到结果再决定下一步。适合路径没法预先枚举、强依赖中间反馈的任务，比如查资料、调试类。缺点是没有全局规划，容易局部最优、绕圈子。

Plan-and-Execute 先出完整计划再逐步执行，适合步骤相对确定的长任务，调用次数少、延迟低。缺点是计划本身可能错，错了要 replan，对模型的规划能力要求高。
生产上常见的是混用：先粗粒度规划，执行到具体节点允许局部 ReAct。

后半段是重点，字节真问过"你的 Agent 调了三个工具就死循环了，异常处理写在哪一层"。我答三层防御：

工具层：每个 tool 调用包 try-catch，异常不抛给框架而是返回结构化错误给模型，比如 {"status": "failed", "error_type": "Timeout", "retry_after": 5}，让模型知道发生了什么而不是拿到一坨堆栈
推理层：max iteration 硬上限 + loop detection，同一个 tool 用同样的参数连续调 N 次、或者状态几轮没有推进，直接熔断，终止当前 reasoning chain，返回失败原因
系统层：全局超时 + 单次任务 token 成本上限，钱烧到线就停

只答"设置最大循环次数"是不够的，面试官会接着问"那没到上限之前它一直在烧 token 怎么办"。

3. Memory 有哪些类型，工程上怎么落地？

短期记忆就是当前会话的上下文。工程问题是 context window 会爆，解法是滑动窗口 + 摘要压缩：token 涨到阈值触发一次 summarize，把历史压成摘要挂回去。

长期记忆是跨会话的东西，用户画像、偏好、历史结论，用向量库或者 KV 存。这里的考点不是用什么存，而是写入策略：不是什么话都值得进长期记忆，要有一步筛选（重要性打分或者规则），否则库里全是噪音，检索出来的记忆反而带歪模型。再加过期管理（TTL 或时间衰减）和去重（新记忆和旧记忆相似度高就合并而不是追加）。

面试官追问的方向一般是：记忆写错了怎么纠正？多 Agent 之间记忆共享不共享？这两个问题没有标准答案，聊 trade-off 就行。

三、对比分析
大厂风格横向对比。 我自己面下来的体感，加上身边朋友的交叉验证，样本有限，仅供参考：

字节：追工程细节。死循环、异常兜底、token 成本、trace、评估指标，场景题全是"线上出问题了怎么办"。它默认你概念都懂，直接考你系统怎么不挂
腾讯：考协议生态。MCP 的原理、A2A、Function Calling 的 schema 设计、和外部工具生态怎么集成。它关心你知不知道行业标准化走到哪了，因为接生态是它的业务
阿里：求架构格局。多 Agent 编排、平台化、网关治理、并发和成本、怎么支撑规模化业务。问题会往上拔一层，考你系统怎么长大
一句话：字节问系统怎么不挂，腾讯问系统怎么和外面连，阿里问系统怎么长大。准备的时候按这个调权重，面字节前把项目的坑全复盘一遍，面腾讯前把 MCP 协议读一遍，面阿里前画一遍架构演进图。

框架范式对比。 ReAct vs Plan-and-Execute 前面说了，补一个面试里加分的第三派：自研状态机。核心链路不赌模型的自主性，主流程写成显式的 DAG 或状态机，LLM 只在关键节点做决策。确定性最高，是很多 to B 生产的真实形态。面试主动提这一层，说明你真上过生产，知道"全自主 Agent"在付费客户面前多悬。

LangChain vs LangGraph：LangChain 是链式抽象，上手快，demo 和标准 RAG 很顺，但它的 Agent 把循环藏在黑盒里，可控性差；
LangGraph 把 Agent 建成图 + 显式状态，循环、分支、中断恢复、人工介入都能表达出来，是复杂 Agent 上生产的选择。
面试官想听的点在于 state 显式化带来的可观测和可恢复，不是背两个框架的 API 区别。

Agent vs Workflow vs Tool 的本质辨析。 这题答好了直接加分：

Tool 是确定性函数，给参数出结果，没有任何自主性
Workflow 是人把流程编排死，LLM 只是其中的节点，走哪条路人说了算
Agent 是把路径决策权交给模型，下一步做什么运行时才知道
判断标准就一个：决策权在谁手里。再补一句工程立场：能用 workflow 解决的别上 agent，自主性是用来对付"路径真的无法预先枚举"的场景的，不是拿来炫技的。这句话说出口，面试官会知道你踩过坑。

# 反问环节问什么
别问"团队氛围怎么样"这种浪费双方时间的问题。Agent 岗我固定问这几个：

咱们 Agent 产品线上的真实任务成功率是多少，怎么统计的？基本可以判断是真落地还是 PPT 项目。答不上来或者说"还在探索阶段"的，大概率还在 demo 期
trace 和评估平台是自研还是用外部方案？判断工程成熟度
模型选型谁定？换模型的评估流程是什么？判断有没有 eval 文化，还是拍脑袋追新模型
我进去头三个月做什么？维护线上系统 = 能摸到真 case，成长快；从 0 开新项目 = 有可能是写 demo 给汇报用，问清楚
最近一次线上 badcase 复盘是什么？敢讲事故的团队一般差不到哪去
就这些。这行的面试正在从"背八股"转向"挖工程"，对我们真做过东西的人是好事。祝大家面得顺利，别被死循环问死。
